# Архитектура: умный поиск по каталогу

Рабочий документ по итогам обсуждения архитектуры (см. `dialogue_log.md` для полного хода рассуждений). Список решённых вопросов и открытых параметров — обновляется по ходу работы.

## 1. Задача и объём реализации

Сравниваем два подхода на `data/queries.csv` (30 запросов) метриками **Precision@1** и **Hit@3**:

- **Fuzzy→Lexical** (бейзлайн)
- **Hybrid = RRF(Fuzzy→Lexical, Semantic)** (полная схема)

Технически это один пайплайн с аблацией, а не два отдельных кода — бейзлайн получаем, просто не подключая семантическую ветку в RRF.

**В объём реализации этого этапа входят все три артефакта сразу, а не только `evaluate.py`**:

1. Сам поиск (два подхода как аблация одного пайплайна).
2. `evaluate.py` — измерение Precision@1/Hit@3.
3. FastAPI `GET /search?query=<>&k=N` — эндпоинт с обогащением результата (артикул, наименование, категория, цена, оценка релевантности). Это не отложенная на будущее продуктовая надстройка — реализуется параллельно с поиском и `evaluate.py`, см. п.6.

## 2. Принципы стека

- **Self-hosted** — приватность важнее скорости/качества из коробки, никакого внешнего API для эмбеддингов.
- **In-memory Python сейчас**, но с чистыми интерфейсами на границах (`LexicalSearcher`, `FuzzyCorrector`, `VectorSearcher`) — чтобы миграция в Postgres при необходимости продукта была дешёвой (оценка ~полдня: 1-2ч инфраструктура, ~1.5ч замена трёх реализаций retrieval, 0.5-1ч ревалидация метрик). **Уточнение по fuzzy-ветке**: `pg_trgm.similarity()` — триграммное/Jaccard-подобное сходство, а не то же самое, что `rapidfuzz.fuzz.ratio` (Левенштейн-производная метрика), под которую откалиброван наш порог ~80% и масштабируемая по длине допустимая дистанция. Миграция fuzzy-ветки на pg_trgm — это не дроп-ин замена реализации одного и того же алгоритма, а смена метрики схожести с повторной калибровкой порога; оценка ~1.5ч на все три ветки retrieval вероятно недооценивает именно эту часть работы.
- **При миграции — целиком в Postgres**, без частичного сплита (частичный сплит воссоздаёт проблему рассинхрона нормализации между Python- и SQL-ветками, которую хотим избежать).
- **Хостинг модели эмбеддингов — отдельный сервис, не в одном образе с приложением.** Всё разворачивается в Docker (никаких `pip install` на хосте). Изначально рассматривался один контейнер с весами, вшитыми в образ на этапе сборки (`RUN` до `COPY` кода — расчёт на кэш слоёв Docker). Отклонено: кэш слоёв — не гарантия (сбрасывается сменой базового образа, `docker builder prune`, `--no-cache`, чистым CI-раннером без локального кэша) — то есть событиями, не связанными с правками самого Dockerfile. Решение: модель — отдельный сервис на официальном образе `ghcr.io/huggingface/text-embeddings-inference` (Rust-сервер эмбеддингов от HuggingFace, поддерживает архитектуру XLM-RoBERTa, к которой принадлежит `multilingual-e5-base` — `--model-id intfloat/multilingual-e5-base`), с весами в **именованном Docker-volume**, полностью не связанном с образом приложения — веса скачиваются один раз и переживают любые пересборки `app`. `VectorSearcher` в коде — HTTP-клиент к этому сервису (`POST /embed`), а не обёртка над `sentence-transformers` в своём процессе. **Проверено запуском** (`/health` → 200, вектор 768-мерный — совпадает с multilingual-e5-base) и честным замером на реальных данных: посчитаны эмбеддинги всех 211 товаров, для каждого из 30 запросов `queries.csv` проверен ранг ожидаемого артикула по чистому косинусному сходству (без лексики/fuzzy/RRF) — **Hit@1 = 23/30 (77%), Hit@3 = 25/30 (83%)** одной только векторной веткой. Это подтверждает ставку на семантический поиск предметно, не на одной случайно выбранной паре (такая попытка была и переоценивала значимость разрыва 0.76 vs 0.85 по одной паре — исправлено на полный прогон по каталогу). Побочная находка из логов: CPU/ONNX-backend этого образа ограничивает батч `max_batch_requests=8` — при офлайн-кодировании каталога слать группами ≤8, не одним большим батчем.

**Попытка проверить BAAI/bge-m3 на этой же машине для сравнения** (~569M параметров, вдвое больше e5-base) — контейнер TEI с bge-m3 упал с `OOMKilled=true` при прогреве модели на машине с 15 ГБ RAM. Загрузка весов заняла ~234с против ~118с у e5-base (эмпирически подтверждает разницу в размере ~2×). Это не просто теоретический аргумент "тяжелее" — практическое свидетельство, что на модест-железе self-hosted развёртывания bge-m3 может не влезать в память вообще, а не только работать медленнее. Дополнительный практический аргумент в пользу уже принятого решения остаться на `multilingual-e5-base`.

## 3. Пайплайн — индексация (офлайн)

```
products.csv
   │
   ▼
нормализация + лемматизация (pymorphy3)
   │
   ├──► fuzzy-словарь: уникальные ЛЕММЫ + частота встречаемости
   │
   ├──► лексический индекс: BM25 (rank_bm25) по леммам
   │
   └──► векторный индекс: эмбеддинги multilingual-e5-base
        (префикс "passage: "), cosine similarity, brute-force numpy
```

**Нормализация текста** (`tokenize()` в `app/search/normalize.py`) перед лемматизацией делает две вещи, найденные и зафиксированные по ходу измерений:
- раскрывает известные точечные сокращения каталога на уровне текста, ДО разбивки на токены (`_ABBREVIATIONS`: «мат.лам.», «глянц.лам.», «подар.», «тисн.» → полные слова) — без этого токенизатор режет их по точке на обрубки, которые pymorphy3 лемматизирует в случайные не относящиеся к делу слова (например «лам» из «мат.лам.» → «лама», животное);
- исключает единицы измерения как токены целиком ПОСЛЕ разбивки (`_UNIT_STOPWORDS`: «см», «мм», «шт», «г», «кг», «л», «мл») — они не несут поискового смысла, а некоторые ложно лемматизируются в случайные слова («см» → «смотреть», глагол); затрагивало ≈48% каталога (101/211 товаров).

Список сокращений расширяется по мере находок (сканом каталога, не угадыванием), не пытаемся заранее покрыть весь возможный ~8000-позиционный каталог.

**Известное остаточное ограничение, не решённое этим фиксом**: лемматизация принципиально не объединяет уменьшительные формы с базовым словом («шарик» ≠ «шар») и производные части речи («подарок» ≠ «подарочный») — это разные словарные единицы для pymorphy3, а не вариант одного слова. Например, запрос «шарики» лемматизируется в «шарик», а товар с «шаров» — либо в «шар» (правильный смысл), либо (что и происходит на практике) pymorphy3 предпочитает разбор «шаров» как фамилии «Шаров» с более высоким score, чем разбор как множественного числа слова «шар» — но даже при верном разборе леммы всё равно разные. Такие случаи не решаются словарём сокращений — нужен либо синонимический слой над леммами каталога, либо обогащение `Наименование` описаниями, которые используют более разговорные формы (см. отдельное обсуждение обогащения синонимами/описаниями).

Индексируется и в fuzzy-словарь, и в лексику/вектор — только поле `Наименование`. `Категория` пока не включаем: на реальных 30 запросах `queries.csv` не нашлось случая, где она была бы нужна (все запросы специфичны на уровне конкретного товара), а для вектора есть риск разбавления эмбеддинга общим для целой категории текстом. **Возможное расширение на будущее** — добавить `Категория` в индексируемый текст и проверить как ablation в `evaluate.py` (дёшево протестировать эмпирически, если понадобятся более обобщённые/категорийные запросы). При включении `Категория` в индекс её нужно синхронно добавить и в fuzzy-словарь — словарь должен строиться из тех же полей, что индексируются для лексики. Тот же принцип на уровне самого прохода лемматизации: каталог лемматизируется **один раз** (`lemmatize_catalog`), и результат передаётся и в fuzzy-словарь, и в лексический индекс — не два независимых вызова лемматизатора по одному и тому же тексту, чтобы не рисковать расхождением между словарём и индексом на разных проходах нормализации.

## 4. Пайплайн — запрос (онлайн)

```
запрос менеджера
   │
   ▼
токенизация
   │
   ▼
лемматизация каждого токена (pymorphy3)
   │
   ▼
OOV-проверка каждой леммы против словаря лемм каталога
   │
   ▼
fuzzy-коррекция только OOV-лемм (порог + правило "один кандидат") → исправленный набор лемм
   │
   ├──► BM25 по исправленным леммам, по ВСЕМУ каталогу → список A (ранги)
   │
   └──► эмбеддинг ИСХОДНОГО (нетронутого) текста запроса
        (префикс "query: ") → cosine similarity по ВСЕМУ каталогу → список B (ранги)
   │
   ▼
RRF(A, B, rrf_k) → финальный ranking → обрезка до top_k (параметр эндпоинта)
```

Ключевые нюансы:

- **Порядок лемматизация → OOV-проверка → fuzzy** (не наоборот). Раньше в этом документе fuzzy шёл до лемматизации с обоснованием "лемматизация ломается на опечатках" — это было неточно. pymorphy3 не ломается на неизвестных словах: для слов не из своего словаря он предсказывает лемму по известным суффиксам (FSM-угадывание) и корректно нормализует грамматическую форму, даже если корень искажён опечаткой ("сирибряная" → лемма-подобная форма "сирибряный", с опечаткой в корне, но правильно снятым окончанием). Значит лемматизация не нуждается в защите fuzzy заранее. А вот старый порядок (fuzzy на сырых токенах против словаря ЛЕММ) был багом: почти любая словоформа кроме именительного падежа единственного числа выглядела как OOV просто из-за несовпадения строк, что создавало риск случайно "исправить" корректно написанное слово в неродственную лемму. Новый порядок сравнивает лемму с леммой — правильное слово в любой словоформе после лемматизации точно совпадёт со словарной леммой и вообще не пойдёт в fuzzy.
- Вектор считается по исходному тексту запроса (не лемматизированному, не fuzzy-исправленному) — защита от того, что плохая fuzzy-коррекция или лемматизация сломает всю систему, а не только лексическую ветку.
- **Именование**: `rrf_k` (константа сглаживания в формуле RRF) и `top_k` (параметр `k=N` в эндпоинте `search?query=&k=N`, сколько результатов хочет вызывающий) — разные сущности, называть по-разному в коде, чтобы не путать.
- **Глубина retrieval перед слиянием**: ранжируем ВЕСЬ каталог в обеих ветках (211-8000 позиций — вычислительно бесплатно и для BM25, и для cosine similarity), без обрезки до какого-то top-N кандидатов перед RRF. Обрезаем только финальный смешанный список до `top_k` в самом конце. Рассмотренная альтернатива — брать `2*top_k` кандидатов от каждой ветки перед слиянием — отклонена: при `rrf_k=0` гармоническое затухание `1/rank` медленное, глубокие (но не нулевые) позиции всё еще дают значимый вклад, и обрезка списка до `2*top_k` превратила бы реальный вклад (`1/rank`) в искусственный ноль ("отсутствует"), искажая результат сильнее, чем при большом `rrf_k`. А поскольку полное ранжирование всё равно бесплатно на нашем масштабе — обрезать нет смысла вообще.
- Товары с нулевым BM25-score (нет ни одного общего слова с запросом) считаются **отсутствующими** в списке A (вклад 0 в RRF), а не получают произвольный ранг среди кучи нулей.

## 5. Оценка (`evaluate.py`)

Прогон всех 30 запросов через обе конфигурации → агрегированная таблица Precision@1/Hit@3 по подходам.

**Важно**: категоризация причин промахов и разметка запросов на "точное совпадение"/"перефразировка" — это ручная работа в Google Sheets, не код `evaluate.py`. Скрипт не анализирует и не классифицирует причины сам — его задача только выдать чистые данные для последующего ручного разбора: по каждому запросу и каждому подходу — эталонный артикул, что нашлось на топ-1/топ-3, ранг эталона (или "не найден") в каждой ветке (лексика/вектор) и в финальном RRF. Формат вывода, удобный для выгрузки в Sheets, — на выбор при реализации (CSV/таблица в консоли).

Механизм получения несрезанного ранга: `evaluate.py` получает его не через `top_k`-обрезанный `SearchPipeline.search()`, а через отдельный метод пайплайна (`search_full()` в `sketch.py`), который возвращает полный, необрезанный RRF-ranking по всему каталогу — иначе для промахов, провалившихся за пределы top_k, ранг эталона физически негде взять.

## 6. FastAPI-эндпоинт (реализуется в этом этапе, не отложено)

`GET /search?query=<>&k=N` — обогащение результата: артикул, наименование, категория, цена, оценка релевантности (итоговый RRF-score). Реализуется параллельно с поиском и `evaluate.py`, использует тот же пайплайн (гибрид с полным `rrf_k`-слиянием — не бейзлайн-аблацию, если не указано иное). **`k` по умолчанию = 3** — согласуется с тем, что качество и так измеряется метрикой Hit@3.

## 7. Дальше по продукту (не в этом этапе, но зафиксировано на будущее)

- Миграция в Postgres: `to_tsvector('simple', <леммы из pymorphy3>)` вместо встроенного русского словаря (тот сводится к Snowball-стеммингу), `pg_trgm` для fuzzy, `pgvector` для эмбеддингов (brute-force через `<=>`, ANN-индекс не нужен на нашем масштабе).
- Риски in-memory в проде, которые нужно закрыть отдельно: пайплайн переиндексации при обновлении каталога из 1С, кэширование эмбеддингов на диск (холодный старт при рестарте), синхронизация нескольких реплик при горизонтальном масштабировании.

## 8. Открытые параметры

Все параметры зафиксированы, см. "Решено" ниже. Единственное сознательно отложенное решение (не параметр к фиксации, а решение отложить) — confidence-порог, см. ниже.

**Отложено (не параметр, а сознательно отложенное решение)**: confidence-порог "отдать топ-1 vs топ-3-5" — это была собственная надстройка сверх требований задачи (3.3 просит только Precision@1/Hit@3 + причины промахов; эндпоинт из п.6 просто отдаёт `top_k` со score). На 30 запросах калибровать порог — риск подгонки под шум небольшой выборки. Решение: эндпоинт всегда отдаёт score, порог/решение "один результат или несколько" — задача потребителя (ассистента), не самого поиска. Если понадобится порог — естественная метрика: относительный разрыв `score_top1 / score_top2`, калибровать на реальном использовании, не на тестовых 30.

**Решено**:

- Индексируется только `Наименование` (и в лексику/вектор, и в fuzzy-словарь) — `Категория` пока не включаем, см. п.3.
- **Fuzzy-порог**: нормализованное сходство (`rapidfuzz.fuzz.ratio`, Левенштейн) ~80%. Вместо отдельного margin — правило "исправляем, только если порог прошёл ровно один кандидат словаря; если два и больше — неоднозначность, не исправляем".
- **Минимальная длина токена для коррекции**: не хардкодим число букв, а масштабируем допустимое расстояние Левенштейна по длине слова — токены ≤6 букв: максимум 1 замена/вставка/удаление; >6 букв: максимум 2.
- **`rrf_k = 3`** (константа сглаживания в RRF, отдельная от `top_k` — параметра эндпоинта). **Свип реально прогнан** (`python evaluate.py --sweep`, `RRF_K_SWEEP` в `app/evaluate.py`) на живом каталоге (211 позиций) и 30 запросах `queries.csv`.

  Свип пересчитан после фикса нормализации (раскрытие сокращений типа «мат.лам.» + фильтр единиц измерения, см. п.3), т.к. изменение BM25-score сдвинуло картину:

  | rrf_k | Hybrid Precision@1 | Hybrid Hit@3 |
  |---|---|---|
  | 0 | 70.0% | **90.0%** |
  | 1 | 70.0% | **90.0%** |
  | 2 | 70.0% | **90.0%** |
  | **3** | **73.3%** | 86.7% |
  | 5 | **73.3%** | 86.7% |
  | 10 | **73.3%** | 86.7% |
  | 15 | **73.3%** | 83.3% |
  | 20 | **73.3%** | 83.3% |
  | 60 | **73.3%** | 80.0% |

  Скачок Precision@1 (70.0%→73.3%) происходит резко на переходе `k=2→3`, не постепенно — плато `{0,1,2}` и плато `{3..10}` разделены чётко, без промежуточной точки. Дальше рост k>10 монотонно теряет Hit@3 без выигрыша в Precision@1 (тот самый механизм "консенсус топит уверенный ответ одной ветки"). **Решено: k>5 больше не проверяем** — за пределами найденного плато `{3..10}` рост k только теряет, выигрыша не показывает ни разу ни на одном прогоне. `RRF_K_SWEEP` сокращён до `{0,1,2,3,4,5}`.

  На n=30 разница между двумя плато — 1 запрос (в пределах шума маленькой выборки). Выбрано `k=3` (нижняя граница второго плато) как компромисс: выше Precision@1 (73.3% против 70.0%), Hit@3 просаживается меньше всего в пределах этого плато (86.7%, не 83.3%/80.0% как при больших k).
- **Глубина retrieval перед слиянием**: ранжируем каталог целиком в обеих ветках, без обрезки до `top-N` кандидатов перед RRF (см. п.4) — обрезка `2*top_k` рассмотрена и отклонена.
- **Tie-break при равном итоговом RRF-score**: сортировка по `(score убыв., min(rank_A, rank_B) возр., артикул возр.)`. При равном score предпочитаем товар с лучшим (меньшим) рангом хотя бы в одной ветке, а не товар, подтверждённый большим числом веток — та же логика, что и в выборе `rrf_k=0`: сильный сигнал одной ветки не должен проигрывать слабому консенсусу двух (см. п.10, отклонённый вариант "tie-break по числу веток").

## 9. Обогащение каталога (сценарии использования)

**Проблема**: часть запросов формулирует задачу/проблему («чем надуть шарики без гелия», «чем приклеить шарики к стене»), а не название товара — ни лексика, ни (частично) вектор не всегда угадывают связь между формулировкой задачи и товаром, который её решает.

**Архитектурное ограничение**: `products.csv` выгружается из 1С заново каждый день и не редактируется нами напрямую — обогащение не может жить в самом файле, оно бы стиралось при следующей выгрузке. Решение: отдельный файл `data/enrichment.csv` (`Артикул;Сценарий`), джойнится к загруженным `Product` по артикулу на этапе сборки пайплайна (`Product.search_text` в `catalog.py`, `apply_enrichment()`, параметр `enrichment_path` в `build_pipeline()`). `Наименование` (`Product.name`) остаётся чистым для отображения — обогащение попадает только в `search_text`, который используется для индексации (лексика + вектор), не в то, что видит пользователь в ответе API.

**Это не генератор контента.** Весь текст сценариев придуман человеком на основе знания о товарах — `app/build_enrichment.py` не создаёт текст автоматически, только механически сопоставляет ключевое слово в `Наименование` с заранее написанным сценарием (`KEYWORD_OVERRIDES`). Смысл держать это кодом, закоммиченным в репозиторий, а не просто статичным `enrichment.csv`: правило "если в названии есть слово X — добавить сценарий Y" переживает завтрашнюю выгрузку из 1С — если появится новый артикул с тем же словом («Насос для шаров XL»), повторный запуск скрипта подхватит его автоматически; статичная таблица, привязанная к сегодняшним артикулам, — нет. По той же причине **сам `data/enrichment.csv` не коммитится** (в `.gitignore`) — коммитится только `app/build_enrichment.py`; файл — детерминированный вывод скрипта, регенерируется командой `python build_enrichment.py` перед использованием `--enrichment` в `evaluate.py`/`api/main.py`.

**Принцип отбора правил — обогащаем только то, что НЕ выводится из названия+категории.** Первая попытка — шаблонный текст на каждую категорию целиком («используется для упаковки подарка в коробку» на все 14 товаров категории «Коробки») — отклонена (см. п.10): категория и название УЖЕ говорят, что это упаковка и что это коробка, шаблон просто пересказывает известное, не добавляя нового факта, и создаёт риск ложного совпадения с конкурентами, случайно делящими другие слова с запросом (конкретный найденный случай — см. п.10). Оставлен только принцип «перевести ЧТО ЭТО в КАКУЮ ПРОБЛЕМУ ОНО РЕШАЕТ» — точечные правки по ключевому слову в названии для товаров, чья функция не самоочевидна («насос» → «чтобы надуть шарики без гелия», «клей-точки» → «чтобы приклеить шарики к стене без скотча», «сетка для сброса» → «чтобы красиво запустить шары в конце праздника» и т.п.). Из 211 товаров текст получили 21 — не все, только те, где принцип применим.

**Методологическая оговорка**: правки написаны по ключевым словам В НАЗВАНИИ товара, не подобраны под конкретные ответы `queries.csv` — иначе результат был бы переобучением на тестовую выборку, а не честной проверкой метода.

**Результат** (`evaluate.py --enrichment data/enrichment.csv`, сравнение с той же архитектурой без обогащения; проверено чистым прогоном с нуля — `docker compose down -v` + `build --no-cache`, числа воспроизводимы):

| подход | без обогащения | с обогащением | Δ Precision@1 | Δ Hit@3 |
|---|---|---|---|---|
| Fuzzy→Lexical | 60.0% / 83.3% | 66.7% / 90.0% | **+6.7 п.п.** (+2 запроса из 30) | **+6.7 п.п.** (+2 запроса) |
| Semantic (чистый вектор) | 76.7% / 83.3% | 80.0% / 86.7% | +3.3 п.п. (+1 запрос) | +3.3 п.п. (+1 запрос) |
| **Hybrid** | 73.3% / 86.7% | **76.7% / 93.3%** | **+3.4 п.п.** (+1 запрос) | **+6.6 п.п.** (+2 запроса) |

Обогащение затрагивает лексику/вектор во всех трёх подходах (`search_text` используется одинаково везде, см. выше), поэтому улучшение видно и в бейзлайне, и в чистом векторе, не только в гибриде. Число промахов гибрида на 30 запросах: 8 без обогащения → 7 с обогащением (закрылись #27 «Сетка для сброса шаров» → «как красиво запустить шары» и #28 «Клей-точки» → «чем приклеить шарики к стене» — оба прямые целевые кандидаты keyword-правил, см. выше).

**Процесс сопровождения — решено оставить полу-ручным, не автоматизировать генеративной моделью.** Рассматривали вариант "добавить ещё одну (генеративную) модель, которая сама пишет сценарии для новых товаров" — отклонено на этом этапе: это отдельная инфраструктурная задача (генеративная LLM — не то же самое, что эмбеддинг-модель TEI; self-hosted вариант — новый сервис, квантованная instruct-модель 1-3B, вероятно поместится в 15 ГБ RAM машины в отличие от bge-m3, но это ещё один Docker-сервис на сопровождении; API-вариант — дешевле поднять, но требует отдельного решения по приватности каталожных метаданных, не наследуемого автоматически из решения про поисковые запросы менеджеров). Автоматизация окупается только при высокой частоте изменений каталога; при низкой частоте дешевле человеку периодически просматривать новые артикулы 1С и решать, нужно ли новое правило в `KEYWORD_OVERRIDES` — ровно тот процесс, который уже используется для текущих 211 позиций.

## 10. Отклонённые варианты (и почему)

- **API-эмбеддинги (не self-hosted)** — отклонено: приватность данных важнее скорости/качества из коробки.
- **Postgres с самого начала для этого этапа** — отклонено. Изначально аргумент был только про `evaluate.py` (одноразовый батч-прогон на статичных 211 строках, преимущества БД не задействуются); после того как в объём этапа добавили `/search`-эндпоинт (см. п.1) — тот же вывод справедлив и для него: это тестовое задание на том же масштабе (211-8000 позиций, один инстанс сервиса, без реального продакшен-трафика/1С-синхронизации), конкурентность и персистентность БД не задействуются и здесь. Полноценный BM25 в Postgres к тому же требует ещё одного расширения (pg_search/ParadeDB) сверх tsvector. Сценарий, где эти соображения БД начинают быть релевантны (несколько реплик, живая синхронизация с 1С) — уже отдельно описан в п.7 "Дальше по продукту" как будущий продакшен, не текущий этап.
- **Fuzzy как третья параллельная ветка в RRF** — отклонено в пользу fuzzy как шага коррекции токенов _перед_ BM25: роль fuzzy — не самостоятельный сигнал релевантности, а починка токенов, поэтому логичнее ставить его до лексики, а не рядом с ней.
- **Частичная миграция в Postgres** (например, только вектор в pgvector, лексика/fuzzy остаются в Python) — отклонено: воссоздаёт рассинхрон нормализации между двумя средами.
- **Tie-break по количеству веток, подтвердивших товар** — отклонено: при `rrf_k=0` товар, найденный только вектором на ранге 1 (score=1.0), может точно совпасть по score с нерелевантным товаром, слабо подтверждённым обеими ветками (ранг 2 и 2 → тоже score=1.0). Предпочесть "больше веток" в этом случае означало бы систематически проигрывать именно paraphrase-случаи, ради которых добавляли вектор — прямое противоречие философии выбора `rrf_k=0`. Заменено на tie-break по `min(rank_A, rank_B)`.
- **Модель эмбеддингов вшита в образ приложения на этапе сборки** (`RUN` до `COPY` кода, расчёт на кэш слоёв Docker) — отклонено: кэш слоёв Docker не гарантия против повторного скачивания весов, его сбрасывают события, не связанные с правками кода (смена базового образа, `docker builder prune`, `--no-cache`, чистый CI-раннер). Заменено на отдельный сервис TEI с весами в именованном volume, независимом от образа приложения.
- **Обогащение каталога generic-шаблоном текста на всю категорию** (например «используется для упаковки подарка в коробку» на все товары категории «Коробки», см. п.9) — отклонено: категория и название уже сообщают эту информацию, шаблон её просто пересказывает, не добавляя нового факта для различения товаров внутри категории. Конкретный найденный вред: на запросе «во что упаковать бутылку вина в подарок, крафт» шаблон поднял нерелевантного конкурента («Коробка под кружку Крафт», у которого уже было слово «Крафт» в названии — шаблон добавил ещё «упаковка»+«подарок»), обогнавшего правильный ответ (ранг эталона 2→7). Замена на точечные keyword-правки восстановила этот случай (ранг 2) и одновременно дала лучший Hit@3 из всех проверенных конфигураций гибрида (93.3% против 90.0% у варианта с категориальным шаблоном).
