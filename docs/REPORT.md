# Отчёт: умный поиск по каталогу

## 1. Результаты

Три конфигурации одного пайплайна (см. `docs/ARCHITECTURE.md`), измерены `evaluate.py`
на всех 30 запросах `queries.csv`, каталог обогащён (`data/enrichment.csv`,
21/211 товаров — см. п.3 ниже).

**Модели и библиотеки** (self-hosted, без GPU и API-ключей): `rank_bm25` —
самодостаточный BM25 без внешней СУБД, соответствует масштабу теста;
`pymorphy3` — единственный поддерживаемый морфоанализатор для русского с
FSM-предсказанием лемм для незнакомых слов (`pymorphy2` не совместим с
Python 3.11+); `rapidfuzz` — C++-реализация Левенштейна, быстрее чистого
Python; `multilingual-e5-base` через `text-embeddings-inference` —
self-hosted эмбеддинги (приватность каталога; сравнение с `bge-m3` — см.
Журнал решений); `FastAPI` — минимальный оверхед и готовая Pydantic-валидация
для одного эндпоинта.

| Подход                                    | Precision@1 | Hit@3     |
| ----------------------------------------- | ----------- | --------- |
| Fuzzy→Lexical (бейзлайн)                  | 66.7%       | 90.0%     |
| Semantic (чистый вектор, диагностика)     | 80.0%       | 86.7%     |
| **Hybrid = RRF(Fuzzy→Lexical, Semantic)** | **76.7%**   | **93.3%** |

**В работу ставим Hybrid** (это и реализовано в `/search`). У чистого вектора
Precision@1 выше (80.0% против 76.7%), но Hit@3 ниже (86.7% против 93.3%) —
и именно Hit@3 важнее для продукта, так как некоторые `query` отвечают больше
чем 1 товару.

Кроме того, чистый вектор — более хрупкий режим: его высокий Precision@1
частично держится на том, что e5-модель не игнорирует буквальное совпадение
слов, а на точных SKU/названиях (не в этих 30 запросах, но в реальном
каталоге) dense retrieval по литературе деградирует чаще, чем лексика. Гибрид
даёт устойчивость по обоим типам запросов за счёт двух независимых сигналов.

Без обогащения каталога гибрид даёт 73.3%/86.7% — обогащение (`data/enrichment.csv`)
даёт **+3.4 п.п. Precision@1 / +6.6 п.п. Hit@3** ценой ручной разметки 21 товара.

**Два числа с учётом спорного эталона** (см. «Замечания к эталону»; метрики по
всем 30 — основные, приведённые в таблице выше):

|                      | n   | Precision@1 | Hit@3 |
| -------------------- | --- | ----------- | ----- |
| Все 30 запросов      | 30  | 76.7%       | 93.3% |
| Без 1 спорного (#20) | 29  | 79.3%       | 96.6% |

Только #20 исключён как вероятно некорректный эталон — не сам ответ товара,
а разметка.

## 2. Разбор ошибок (Hybrid, лучший подход)

7 промахов Hit@1 из 30 (2 из них — также промахи Hit@3), сгруппированы:

**Спорный/неоднозначный эталон (1, #20)**
«чем надуть шарики без гелия» → эталон ШВ-9209 «Набор шаров», хотя запрос явно
про устройство для надувания; наша система на первом месте находит именно
насос (РУН-13119) — вероятно, правильный ответ отличается от эталона.

**RRF tie-break на равном score (2, #15, #19)**
- #15 «гирлянда занавес 3 на 2» — эталон и конкурент получают идентичный
  итоговый score (0.45); хотя эталон («Гирлянда-занавес 3х2 м») точнее по
  смыслу, решает tie-break по артикулу.
- #19 «куда положить деньги маме на день рождения» — тот же механизм: эталон
  («Любимой маме») и конкурент («С Днем Рождения», тоже валидный конверт для
  денег) получают равный score (0.45/0.45), решает tie-break. В отличие от
  #20 эталон здесь не под вопросом — оба кандидата в каталоге уместны, просто
  RRF не развёл их по score.

**Ложное совпадение с конкурентом по отдельному слову (2, #18, #26)**
- #18 «зелёная бумажная стружка, чтобы заполнить коробку» — и лексика, и
  вектор цепляются за слова «зелёный»/«коробка» в названии совсем другого
  товара («Набор коробок... Зеленые листья»), хотя нужен наполнитель.
- #26 «во что упаковать бутылку вина в подарок, крафт» — конкурент («Набор
  коробок... Крафт без рисунка») обгоняет эталон на минимальном разрыве
  (0.32 vs 0.29) только за счёт слова «крафт»; усугубляется тем, что лемма
  «подарок» (запрос, существительное) ≠ «подарочный» (товар, прилагательное).

**В названии товара нет отличительного слова из запроса (2, #23, #30)**

- #23 «гирлянда на ёлку» — несколько похожих гирлянд в каталоге, ни у одной в
  названии нет слова «ёлка»/«ёлочная» — эталон текстуально неотличим от
  конкурентов, итоговый ранг 18 (вне топ-10).
- #30 «...метра два» — эталон (гирлянда 2 м) проигрывает по score гирляндам
  5 м: числовая характеристика длины не даёт отдельного веса ни в лексике, ни
  в векторе.

## 3. Замечания к данным и эталону

- **#20 «чем надуть шарики без гелия»** — см. выше, вероятно некорректный
  эталон: в каталоге есть насосы, которые семантически точнее отвечают на
  вопрос «чем», чем набор шаров.
- Возможный **дубликат позиций в каталоге**: ТМ-3862 и ТМ-2999 — похожие
  названия («салфетки с единорогом»), риск систематически путать эталон.
- **Сокращения в `Наименование`** («мат.лам.», «тисн.», «подар.») ломают
  токенизацию без ручной расшифровки — расширяемый словарь покрывает только
  найденные на этих 211 позициях случаи, не гарантирует полноту на ~8000.
- **Единицы измерения** («см», «мм») паразитно лемматизируются в случайные
  слова (например «см» → «смотреть», затрагивало ≈48% каталога) — исправлено
  фильтром стоп-токенов.
- **Числовые атрибуты** (длина, диаметр) не выделяются как структурированный
  признак — запросы вида «метра два» полагаются только на текстовое
  совпадение (см. #30).

## 4. Журнал решений

| Что предложил ИИ-ассистент | Что взяли | Что отвергли и почему |
|---|---|---|
| 5 вариантов поиска (лексика, fuzzy отдельно, вектор, LLM-реранкинг, гибрид); рекомендовал гибрид | Гибрид как основа; сравнение — Fuzzy→Lexical vs Hybrid как аблация одного пайплайна, не два решения; `vector_only` — только диагностика | LLM-реранкинг основным механизмом — дорого на весь каталог; чистые лексика/fuzzy по отдельности — не покрывают перефразировки/опечатки |
| Сравнить self-hosted vs API-эмбеддинги | Self-hosted (`multilingual-e5-base` через TEI) | API — приватность каталожных данных важнее скорости/качества из коробки |
| In-memory Python (дешёвая миграция позже) — в ответ на вопрос пользователя про Postgres | In-memory Python | Postgres с самого начала — пользователь сам к нему склонялся; отклонил: оверхед не окупается на масштабе теста (211-8000 позиций, 1 инстанс), нужда в будущем неясна |
| Fuzzy как третья параллельная ветка в RRF | Fuzzy как шаг коррекции токенов перед BM25 (интуиция пользователя, ИИ обосновал) | Третья ветка — роль fuzzy это починка токена, не самостоятельный сигнал релевантности |
| Tie-break по числу веток, подтвердивших товар | Tie-break по лучшему рангу хотя бы в одной ветке; затем — по артикулу | По числу веток — топит paraphrase-случаи (товар, найденный только вектором на ранге 1, проигрывал бы слабо подтверждённому обеими ветками) |
| Обогатить `search_text` шаблоном на всю категорию | Точечные keyword-правила только там, где функция товара не самоочевидна (21/211) | Категориальный шаблон — не добавляет факта, создал регресс (#26: ранг 2→7) |
| Проверить `BAAI/bge-m3` как альтернативу | `multilingual-e5-base` | bge-m3 — `OOMKilled` при прогреве (15 ГБ RAM, вдвое тяжелее) |
| Тест Макнемара для статзначимости Fuzzy→Lexical vs Hybrid | Не делать | Надстройка сверх требований задания на этом этапе |

## 5. Границы

Не сделано / сознательно отложено:

- Индексация происходит один раз при старте — изменения `products.csv` во
  время работы не подхватываются без рестарта.
- Однокоренные слова («шарик»≠«шар», «подарок»≠«подарочный») не решены на
  уровне лексики — держится только на векторной ветке; нужен синонимический
  слой над леммами или более разговорные формулировки в обогащении.
- Обогащение — 21/211 товаров, правила пишутся вручную; на полном каталоге
  (~8000) нужно либо расширять их вручную, либо отдельный generative-сервис с
  контролем качества.
- Поле `Категория` не индексируется — не понадобилось на этих 30 запросах,
  к тому же есть ощущение, что оно скорее добавит шума (общий текст категории
  размывает эмбеддинг и лексику конкретного товара), чем пользы.
- Результаты на 30 запросах по базе из 211 товаров не гарантируют подобный
  исход на базе из 8000.
- Нет unit-тестов — только сквозная проверка через `evaluate.py` и ручные
  запросы к живому API.
- Риски in-memory на масштабе продакшена (переиндексация при обновлении из
  1С, персистентность эмбеддингов, синхронизация реплик) — задокументированы
  в `docs/ARCHITECTURE.md` п.7, не реализованы: вне объёма задания.
- Будь больше времени — почитал бы больше про LLM-реранкинг, возможно применил бы его.
